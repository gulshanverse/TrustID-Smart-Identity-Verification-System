# TrustID Phase 1.1 — Document Intelligence Audit and Benchmark

**Date:** 2026-09-16  
**Scope:** Phase 1 production document intelligence pipeline: bounded local OCR, document quality assessment, ICAO TD3 MRZ parsing, checksum validation, OCR/MRZ consistency, persistence-facing behavior, and frontend integration.

## Executive summary

Phase 1.1 confirms that TrustID has a safe production-oriented intelligence path while preserving the existing `DEMO / SIMULATED` provider. The production provider is explicitly separate from the demo provider, rejects demo-marker assumptions, limits PDF rasterization to five pages at 220 DPI with one conversion thread, and reports sanitized engine failures. The MRZ implementation now detects only two-line ICAO TD3 candidates of exactly 44 characters per line and validates field and composite checksums. Document quality assessment rejects malformed PDFs and low-resolution images without claiming identity authenticity.

The backend quality gate passed: **81 tests, Ruff, and mypy**. The frontend gate passed: **TypeScript typecheck and Next.js production build**. The deterministic corpus contains **17 fictional fixtures**, including valid, invalid, and malformed MRZ inputs, image-quality variants, one-page and three-page PDFs, a malformed PDF, and a 3000×3000 pathological image. The benchmark was run in an environment without the Tesseract executable; accordingly, OCR is recorded as unavailable rather than being fabricated. This is an audit limitation, not a production OCR result.

One production hardening defect found during audit was corrected: production OCR previously returned a fixed `0.5` confidence whenever text existed. It now uses Tesseract `image_to_data` word confidences, filters non-token and negative values, and averages the remaining scores across processed pages. If the runtime cannot provide confidence data, the provider returns `0.0` rather than inventing confidence.

**Release recommendation:** conditionally ready for deployment after the target Render image is verified to contain the Tesseract binary and language data, and after a staging smoke test with a fictional image/PDF. The audit does not authorize claims of document authenticity, liveness, or identity assurance from OCR alone.

## Benchmark method

The corpus is generated by `scripts/phase11_benchmark.py` and retained under `docs/phase-1.1-corpus/`. All names, numbers, dates, MRZ values, and document text are fictional or standard synthetic test content. The benchmark directly exercises the quality and MRZ domain functions and records wall-clock processing time and Python process RSS. It deliberately does not invoke an unavailable OCR executable.

The image corpus includes clean, low-resolution, rotated, low-contrast, overexposed, underexposed, blurred, compressed, mismatch, no-MRZ, and pathological-size cases. The PDF corpus includes extractable one-page text, extractable three-page text, and malformed PDF bytes. The MRZ corpus includes the canonical valid TD3 sample, a checksum-mutated invalid sample, and malformed text.

## Functional audit

### OCR provider separation

`DemoOCRProvider` remains available and only processes explicitly marked demo fixtures. `ProductionOCRProvider` uses local `pytesseract` and does not synthesize identity fields for arbitrary input. Field extraction is conservative and pattern-based; MRZ-derived fields are added only when a passport MRZ candidate is detected. Per-token Tesseract confidence is now measured through the data API rather than fixed.

Production OCR is bounded by a 15-second Tesseract timeout per image operation and a five-page PDF rasterization limit. PDF conversion uses one thread. The upload/document path separately enforces the application’s file allowlist and size limits documented in `docs/document-upload.md`.

### Quality assessment

The quality engine records dimensions or PDF page/text metrics and emits `GOOD`, `REVIEW`, or `FAILED` with reasons. It correctly rejects malformed PDF bytes and flags the low-resolution fixture. The current image heuristic is intentionally conservative: sparse black text on a white synthetic canvas can be flagged for low contrast even when dimensions are large. This is a review signal, not an authenticity decision. A later calibration phase should use representative, consented or synthetic scans to tune thresholds and add a dedicated focus/blur metric.

### MRZ intelligence

The parser implements TD3 structure detection, normalized line handling, individual field checksums, and the composite checksum. It extracts document number, issuing state, nationality, dates, sex, and name components. Date parsing is bounded and invalid calendar dates become unavailable rather than being silently accepted. OCR/MRZ comparison returns `MATCH`, `MISMATCH`, or `NOT_AVAILABLE`; it does not override the underlying evidence.

### Safety and observability

The pipeline preserves safe diagnostic behavior: engine exceptions are reduced to exception type in user-facing errors, storage diagnostics do not include credentials or full sensitive URLs, and arbitrary documents do not enter demo mode. Permission-protected API routes remain unchanged. No production credentials, external OCR APIs, or paid services were introduced.

## Tesseract versus self-hosted alternatives

| Option | Strengths | Cost/resource implications | Phase 1.1 decision |
|---|---|---|---|
| **Tesseract 5 + pytesseract** | Apache 2.0, mature Linux package, local execution, TSV/data confidence, small operational surface | CPU-bound; requires binary and language data in the deployment image; quality depends strongly on preprocessing and document layout | **Keep for Phase 1.** Best fit for 0.1 CPU/512 MB constraints, provided runtime installation is verified |
| **EasyOCR** | Apache 2.0, broad language support, CPU mode, bounding boxes and confidence values | PyTorch plus downloaded model weights create a much larger memory and cold-start footprint; official README notes model download and CPU-only configuration | **Do not add now.** Revisit only with measured memory headroom and a language requirement Tesseract cannot meet |
| **PaddleOCR** | Apache 2.0, document-layout and multilingual ecosystem, lightweight model tiers available | Paddle runtime/model assets and initialization are materially heavier than Tesseract; document parsing variants increase operational complexity | **Do not add now.** Candidate for a separate worker/service, not the free-tier API process |
| **Paid/cloud OCR** | Potentially higher accuracy and managed scaling | Violates the zero-cost/self-hosted constraint and creates data-governance/vendor dependencies | **Rejected for this phase** |

Tesseract is Apache 2.0 and its official documentation describes the 5.x engine and language data distribution [Tesseract documentation](https://tesseract-ocr.github.io/tessdoc/). EasyOCR’s official repository documents CPU-only mode, automatic model downloads, and confidence-bearing detections [EasyOCR repository](https://github.com/JaidedAI/EasyOCR). PaddleOCR is Apache-2.0 and documents its multilingual OCR and document-structure ecosystem [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR). These are architecture comparisons, not accuracy claims for TrustID’s documents.

## Render free-tier readiness

The implementation is suitable for a constrained API process because it avoids loading large neural OCR models, limits PDF pages, uses one PDF conversion thread, and applies an OCR timeout. The benchmark process reached approximately 96 MiB RSS, but this must not be interpreted as a full-service peak: Render memory also includes Python/FastAPI, SQLAlchemy, database driver, request buffers, and concurrent requests.

Before production promotion, verify all of the following in the deployed image:

1. `tesseract --version` succeeds and the required `eng` trained data is installed.
2. `pytesseract.get_tesseract_version()` succeeds from the API process.
3. A fictional PNG and a fictional extractable PDF complete within the endpoint timeout.
4. A six-page PDF is bounded to the first five pages and does not cause unbounded work.
5. Malformed PDF and oversized/pathological inputs return safe validation or quality failures.
6. Concurrent upload/OCR requests are rate-limited or serialized at the application/deployment boundary to protect 512 MB RAM.
7. Logs contain operation and exception type, but no document text, credentials, authorization headers, cookies, or database URLs.

## Known limitations and follow-up work

The benchmark environment did not contain Tesseract, so end-to-end OCR latency, character accuracy, field precision/recall, and confidence calibration remain unmeasured. The next validation run should execute in the exact Render build image with a larger fictional corpus and report CER/WER, field exact-match rate, MRZ detection precision/recall, p50/p95 latency, and peak RSS under one and concurrent requests.

The current quality score is a triage heuristic, not a forensic quality model. It should be calibrated against document-type-specific synthetic fixtures. The current production field extractor is intentionally conservative and should not be expanded into broad regex matching without a labeled fixture set. MRZ validity also does not establish that a passport is genuine or belongs to a person.

## Conclusion

Phase 1.1 is complete as an engineering audit and hardening pass. The platform now has honest OCR confidence semantics, deterministic negative and positive evidence, bounded processing, and an explicit deployment verification checklist. It is appropriate to proceed to staging deployment and runtime validation; it is not appropriate to market the current OCR/MRZ layer as standalone identity authenticity verification.
