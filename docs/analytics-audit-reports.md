# TrustID analytics, audit, and reports

Phase 11 exposes accumulated TrustID records as operational analytics, an authorized audit explorer, and deterministic reports. Analytics are derived from TrustID's persisted application records and do not represent official government statistics.

## Counting semantics

Analytics count distinct persisted `verifications` within the selected UTC period. Repeated OCR, validation, tampering, face, or risk analysis rows are analysis runs, not new verifications. The overview's completed count is the number of distinct verifications with a latest persisted risk assessment in the selected period; pending is total minus completed. Historical risk distribution uses the latest persisted assessment per verification and does not recompute an old assessment with current rules.

Case metrics count persisted cases linked to verifications. They distinguish total cases, status distribution, priority distribution, and cases linked to a high-risk assessment. A case does not duplicate its verification. Module metrics are grouped from persisted OCR, validation, tampering, finding, and face rows. Empty data is represented by zero counts where a count is meaningful and `null` or `Unavailable` where a metric cannot be calculated.

All API date boundaries are normalized to **UTC**. Supported preset ranges are 7, 30, and 90 days; custom ISO date boundaries are also accepted by the API. Trend queries group persisted verification creation timestamps by UTC calendar date.

## Analytics API and permissions

The server-side endpoints are:

- `GET /api/v1/analytics/overview`
- `GET /api/v1/analytics/verifications`
- `GET /api/v1/analytics/risk`
- `GET /api/v1/analytics/cases`
- `GET /api/v1/analytics/trends`

All endpoints require the `ANALYTICS` permission. Officers receive authorized operational metrics; supervisors and administrators receive broader access through existing RBAC; frontend role labels are never trusted. Filters include date range, risk level, case status, case priority, and document type only where persisted data supports the filter.

## Audit architecture

The audit explorer reads the existing append-oriented `audit_events` table. It does not create a second audit database and does not treat page loads, report views, or analytics requests as new verifications. It supports server-side filtering by event type, actor, verification, case, document, status, date boundaries, and pagination through `GET /api/v1/audit/events`. Detail responses expose safe identifiers, provider, status, and timestamps. Raw OCR text, biometric images, embeddings, passwords, secrets, and sensitive request payloads are never returned.

The existing `AUDIT` permission protects the explorer. Normal application routes do not expose audit mutation or deletion operations.

## Reports

Reports are deterministic server-side PDFs generated by `ReportService` from authoritative persisted records. The report version is currently `phase11-v1`. Report metadata is stored in `reports`; PDF contents are not stored in PostgreSQL.

Supported generation endpoints:

- `POST /api/v1/reports/verification/{verification_id}`
- `POST /api/v1/reports/case/{case_id}`
- `GET /api/v1/reports/recent`

Generation requires authentication and the existing `REPORTS` permission. Each generation creates `REPORT_GENERATED` in the existing audit stream. Report downloads use authenticated API responses and `Content-Disposition`; there are no public report URLs. Generated reports include a report ID, UTC timestamp, reference, persisted OCR/validation/tampering/face/risk summaries where available, case evidence references, notes/decision counts, and a safety disclaimer. They never include raw biometric material or unnecessary raw OCR content.

Reports use persisted historical values instead of recomputing risk or other analysis. Missing module results are rendered as `Unavailable`, not fabricated success. Report data summarizes AI-assisted signals and human workflow records; it does not independently establish identity, fraud, criminality, immigration eligibility, or legal status.

## Demo and privacy boundaries

The analytics dashboard labels demo data when applicable and does not make claims about government throughput, public safety, border operations, or official statistics. No new AI model, government integration, blockchain, surveillance, demographic profiling, emotion analytics, liveness, automatic fraud classification, or automatic officer decision logic is introduced by this phase.
